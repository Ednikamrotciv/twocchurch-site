APPLY THIS UPDATE (307) — LOCAL + LIVE
=====================================
This update fixes the local → live chain, so a local publish carries
everything to live and stays there. Symptom it kills: after publishing
locally the terminal said "auto-deploy: could not bake the new words",
uploads/photos from a live backup did not come home on local, and the
live site behaved like a new update again after every Render sleep.
What changed (note 307):

- The dev backend (`npm run dev`) now accepts backup restores and photo
  deletes exactly like the office server (`/__restore-file`,
  `/__delete-file`, same naming guards). Before, a live backup restored
  on local lost every embedded photo/video (the dev server had no door
  for them), and the office photo delete failed on local.
- A failed bake now says WHY in the terminal (the bake's own first error
  lines) instead of failing silently — plus how to fix it now
  (`npm run bake-seed` by hand). The bake also runs on the exact node
  that runs the backend (no more bare-`node`-missing-from-PATH failures),
  fails loudly without ever wiping a good seed.json, and a failed push
  now names the usual suspect: a video in data/uploads/ near/over the
  host's 100 MB file limit looks exactly like a login failure.
- Unchanged and still locked: every new update holds on maintenance until
  the office publishes (plain reload, /admin clear); with no new update
  the copy stays on the last published; only an explicit office action
  lifts maintenance; sleep/wake re-serves the last publish whole
  (words + stamp + history) once the bake is fresh.
- The pre-ship verifier has a new section K locking this fix — one FAIL
  blocks the ship. It passed for this zip.

LOCAL (your computer)
1. In the OLD folder: open #/admin → Tools → Back up now. Keep the file.
2. Extract THIS zip to a NEW folder (do not extract over the old one).
3. In the new folder: npm install
4. Use `npm run dev` for local work (http://localhost:5173/, admin: /admin).
   Do NOT run `npm start` on the office machine: sharing ships ON in this
   folder, and a local `npm start` would re-point cms-server.txt at this
   machine's tunnel (the live site must keep pointing at Render).
5. BEFORE restoring: the site must show the maintenance notice ("We'll be
   right back", logo + message only) — this update holds until blessed.
   A plain reload must show it; no hard refresh needed. The admin console
   (/admin) must NOT show it — it boots straight into the console.
6. #/admin → Tools → Restore the backup file → check the toast names the
   photos/videos brought home (filesRestored) → Review and publish →
   Publish. Local lifts to 307 and the notice releases, uploads showing.
   Reload desktop + phone width to verify (plain reloads).
7. Watch the terminal ~2 minutes after publishing. You must see EITHER
   "auto-deploy: new words pushed" OR "auto-deploy is off (reason)". If
   you see "could not bake", it now says WHY — run `npm run bake-seed`
   by hand and read its error, fix it, publish again. Then check
   `git log --oneline -3`: you must see a "content update …" commit. If
   not, push by hand: bake first (`npm run bake-seed`), then
   `git add -A -- data seed.json && git commit -m "content update" && git push`.
   WITHOUT this push the live bake goes stale and a live wake waits on
   maintenance again.
8. If the push fails, check data/uploads/ for videos near/over 100 MB
   (the host refuses them) — the terminal now says so. Shrink the file,
   publish again.
9. Check: reload again with no new update — the site stays on the last
   published (no notice, published words intact). Console check:
   window.__maintState() shows publishedNotes 307.

LIVE (Render: twocchurch-site.onrender.com)
1. Put this code where Render builds it (replace src/, scripts/, index.html,
   seed.json, vite.config.ts, package.json — keep data/ as-is), commit/push.
   Render: install npm install, build npm run build, start node scripts/serve.mjs.
2. Confirm https://twocchurch-site.onrender.com/version.json shows {"notes":307}.
3. Push the step-7 content commit if you have not already (the bake must be
   from 307 or newer — a bake stamped 306 or older still waits, by design).
   Render rebuilds on the push by itself.
4. The live site now waits on the maintenance notice until the publish lands
   through the bake — verify with a PLAIN reload on desktop + phone width,
   uploads/photos/videos showing. The live admin console stays clear
   throughout and keeps "Last published". No live /admin publish needed;
   only use it as a stopgap (it lives on the ephemeral disk only — always
   publish the same words locally afterwards).
5. Sleep test (optional, proves the fix): in the Render dashboard, restart
   the service (or just wait for it to sleep). The site must stay live with
   "Last published" intact — no notice, no re-publish. If the notice shows,
   the bake is stale: do step 7 first, then test again.
6. Optional but recommended on free Render: a free keep-awake ping
   (e.g. UptimeRobot, every 5 minutes, to
   https://twocchurch-site.onrender.com/version.json) skips the 30–60s cold
   boot after a sleep. Harmless either way now — sleep loses nothing — it
   only makes first loads faster.

If desktop ever looks live while mobile waits: desktop is in ?preview=1
(gold Preview bar) — click Exit preview. Or clear that tab's preview flag.
