APPLY THIS UPDATE (316) — LOCAL + LIVE
=====================================
This update makes live immediate: the moment the broadcast starts on the
YouTube channel, the site shows it and the waiting clock vanishes — on the
live site and on local runs alike. Symptom it kills: starting the stream on
YouTube took minutes to reach the Watch page (the on-air check asked every
45s on the clock / 3min off it, waited out a freshness window on open, and
never re-asked when the channel was retyped), so the ticking clock sat on
screen long after the service was up. What changed (note 316):

- The fast cadence is now 20s (was 45s), quiet-week 90s (was 3min). The Watch
  page checks AT ONCE on open and stays fast whether or not a gathering is on
  the clock — a visitor who opened that page came to see the stream. The
  player still wins over the clock the instant the answer says live, including
  unscheduled broadcasts (vigils, moved services).
- The channel is editable and the check follows it: retyping the YouTube
  channel in the console (or a publish landing) re-checks at once through a
  debounced announcement plus signature tracking — no waiting out the timer.
  Only the fetch door differs per copy (same-origin /__yt locally, the office
  server when joined, else the public proxy), so live and local behave alike.
- Start / Continue / Stop re-ask the channel at once.
- Same update closes an offline gap from 309: a per-section Publish while
  offline now saves last-published on this copy with its cache (the whole-site
  path already did; a bless-only click now caches too). An offline click keeps
  this copy live, the flush carries it out when the connection returns, and a
  host sleep in between changes nothing.
- Unchanged and still locked: maintenance holds until the office publishes
  (plain reload, /admin clear); with no new update the copy stays on the last
  published; only an explicit office action lifts maintenance; sleep/wake
  re-serves the last publish whole (words + stamp + history); every Publish
  still folds live's newer words in (untouched sections follow live, office
  edits win, uploads come home).
- The pre-ship verifier's section M now locks live-at-once (short cadence,
  urgent Watch check, moved-channel re-check, button re-asks, offline stamp)
  — one FAIL blocks the ship. It passed for this zip.

LOCAL (your computer)

2. Extract THIS zip to a NEW folder (do not extract over the old one).
3. In the new folder: npm install
4. Use `npm run dev` for local work (http://localhost:5173/, admin: /admin).
   Do NOT run `npm start` on the office machine: sharing ships ON in this
   folder, and a local `npm start` would re-point cms-server.txt at this
   machine's tunnel (the live site must keep pointing at Render).
5. BEFORE restoring: the site must show the maintenance notice ("We'll be
   right back", logo + message only) — this update holds until blessed.
   A plain reload must show it; no hard refresh needed. The admin console
   (/admin) must NOT show it — it boots straight into the console.
   (Coming from 305: same steps — backup in the old folder first, then a NEW
   folder for 316, restore, publish. The restore carries all words across the
   jump; the first publish also folds in anything newer on the live site.)
6. Bring your words home: #/admin → Tools → Restore the backup file → review
   → Publish. The Publish itself folds in anything newer on the live site
   (untouched sections follow live, your edits win, uploads come home), so
   there is no second step.
   Local lifts to 316 and the notice releases. Reload desktop + phone
   width to verify (plain reloads).
7. Live check (local): open /watch-live, then start the broadcast on the
   YouTube channel (or retype the channel in the console and publish). The
   player must appear within seconds and the ticking clock must vanish with
   it — no minute-long wait. Stop the stream and the page returns to the
   countdown by itself.
8. From here the sync is automatic both ways: publish on LOCAL and the
   bake + push carry it to live in a few minutes (watch the terminal for
   "auto-deploy: new words pushed", then `git log --oneline -3` shows the
   content commit); publish on LIVE and the signed-in office copy saves it
   by itself within about a minute (toast confirms, uploads included) — or
   it folds into the next local Publish, whichever comes first — and the
   deploy carries it back out on the next cycle. WITHOUT the step-8
   push the live bake goes stale and a live wake waits on maintenance
   again — if the terminal reports a bake/push problem it now says why.
   Offline clicks are safe: this copy stays on its last published (stamp +
   words cached in the browser, queue flushed on reconnect), and a sleep in
   between changes nothing.
9. Check: reload again with no new update — the site stays on the last
