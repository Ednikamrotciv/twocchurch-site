APPLY THIS UPDATE (308) — LOCAL + LIVE
=====================================
This update finishes the two-way sync: anything published on live is saved
on the office copy by itself, anything published on local reaches live
through the deploy — no direction is ever lost. Symptom it kills: a
publish done on live /admin stayed on live's short memory only. The next
sleep wiped it, and the office copy never saw it at all.
What changed (note 308):

- While an office tab is open and signed in, a live publish newer than the
  office copy publishes itself straight onto the office backend (same bless,
  history and log as a hand publish, toast to say so) with its uploads
  fetched home. Conservative by design: never across a newer update (apply
  the zip on local first), never over unsaved draft work, never from a
  fallback bake (only a fresh copy may be restored from the bake, and only
  by hand), and ties go to the durable path — rev counters are per-store,
  so the wall clock arbitrates and only a strictly newer live publish wins.
- Tools → "Pull from live now" lands live's words as a draft — review, then
  Publish — the backup-restore shape the office already knows (refuses to
  overwrite unsaved changes; uploads come home; retired sections are named
  and left out).
- Office backends name their live address (`/__live-url` from
  cms-server.txt, on `npm run dev` and `npm start` alike). The live box
  answers empty — it IS live, so its tabs never pull. No live address, no
  pull; visitors' tabs never poll.
- Local → live is unchanged: publish locally, the bake + commit + push go
  out by themselves in ~2 minutes, Render rebuilds, the bake carries the
  whole publish (words + stamp + history + uploads).
- Unchanged and still locked: every new update holds on maintenance until
  the office publishes (plain reload, /admin clear); with no new update
  the copy stays on the last published; only an explicit office action
  lifts maintenance; sleep/wake re-serves the last publish whole.
- The pre-ship verifier has a new section L locking this fix — one FAIL
  blocks the ship. It passed for this zip.

LOCAL (your computer)
1. In the OLD folder: open #/admin → Tools → Back up now. Keep the file.
2. Extract THIS zip to a NEW folder (do not extract over the old one).
3. In the new folder: npm install
4. Use `npm run dev` for local work (http://localhost:5173/, admin: /admin).
   Do NOT run `npm start` on the office machine: sharing ships ON in this
   folder, and a local `npm start` would re-point cms-server.txt at this
   machine's tunnel (the live site must keep pointing at Render).
5. BEFORE restoring: the site must show the maintenance notice ("We'll be
   right back", logo + message only) — this update holds until blessed.
   A plain reload must show it; no hard refresh needed. The admin console
   (/admin) must NOT show it — it boots straight into the console.
6. Bring your words home EITHER way (they are the same words):
   (a) #/admin → Tools → Restore the backup file → Review and publish →
       Publish; OR (b) sign in, then Tools → Pull from live now → review →
       Publish (live's words AND photos land as a draft).
   Local lifts to 308 and the notice releases. Reload desktop + phone
   width to verify (plain reloads).
7. From here the sync is automatic both ways: publish on LOCAL and the
   bake + push carry it to live in a few minutes (watch the terminal for
   "auto-deploy: new words pushed", then `git log --oneline -3` shows the
   content commit); publish on LIVE and the signed-in office copy saves it
   by itself within about a minute (toast confirms, uploads included) and
   pushes it back out to the deploy on the next cycle. WITHOUT the step-7
   push the live bake goes stale and a live wake waits on maintenance
   again — if the terminal reports a bake/push problem it now says why.
8. Check: reload again with no new update — the site stays on the last
   published (no notice, published words intact). Console check:
   window.__maintState() shows publishedNotes 308.

LIVE (Render: twocchurch-site.onrender.com)
1. Put this code where Render builds it (replace src/, scripts/, index.html,
   seed.json, vite.config.ts, package.json — keep data/ as-is), commit/push.
   Render: install npm install, build npm run build, start node scripts/serve.mjs.
2. Confirm https://twocchurch-site.onrender.com/version.json shows {"notes":308}.
3. Push the step-7 content commit if you have not already (the bake must be
   from 308 or newer — a bake stamped 307 or older still waits, by design).
   Render rebuilds on the push by itself.
4. The live site now waits on the maintenance notice until the publish lands
   through the bake — verify with a PLAIN reload on desktop + phone width,
   uploads/photos/videos showing. The live admin console stays clear
   throughout and keeps "Last published". A live /admin publish now also
   lands on the office copy by itself (about a minute, while the office is
   signed in) — but still publish the same words locally afterwards when
   you can: the ephemeral disk forgets, the office folder remembers.
5. Sleep test (optional, proves the fix): in the Render dashboard, restart
   the service (or just wait for it to sleep). The site must stay live with
   "Last published" intact — no notice, no re-publish. If the notice shows,
   the bake is stale: do step 7 first, then test again.
6. Optional but recommended on free Render: a free keep-awake ping
   (e.g. UptimeRobot, every 5 minutes, to
   https://twocchurch-site.onrender.com/version.json) skips the 30–60s cold
   boot after a sleep. Harmless either way now — sleep loses nothing — it
   only makes first loads faster.

If desktop ever looks live while mobile waits: desktop is in ?preview=1
(gold Preview bar) — click Exit preview. Or clear that tab's preview flag.
