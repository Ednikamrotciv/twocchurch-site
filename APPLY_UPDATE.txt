APPLY THIS UPDATE (312) — LOCAL + LIVE
=====================================
The YouTube half of the livestream fix: a channel-only YouTube setup now
plays the moment the service is on air (through the channel's own live
embed), the Watch-on-YouTube button follows the channel when no link is set,
and a freshly pasted channel is re-checked at once instead of waiting out
the quiet timer. (310 fixed the same wait for a set Facebook link; 312 does
it for a set YouTube channel. Backups still hit the joined disk and the push
is still followed until live catches up.)
What changed (notes 310 + 312):

- Livestream plays when it starts. The Watch page (and the site-wide on-air
  answer) now asks Facebook too when its link is set — a Facebook-only
  broadcast used to be invisible everywhere, so the clock never left. And
  when the site is on air (switch or schedule) with a stream link set, the
  link plays at once — unless the check affirmatively says the stream is
  down, in which case the waiting clock stays (a stale link never plays as
  live). A detected broadcast whose page gives no id yet plays through the
  channel's own live embed instead of the clock.
- YouTube channel-only plays too (note 312). 310 played a set stream link at
  once on air — but only the link counted, so a YouTube setup with just the
  channel pasted still sat on the clock until the check answered, and a new
  channel waited out the quiet timer. Now the channel counts as a set link:
  on-air + channel plays the channel's live embed at once (still never when
  the check affirmatively says off), the platform list carries YouTube in the
  on-air window, the Watch-on-YouTube button opens the channel's /live page
  when no video id is set, and any new address is re-checked at once.
- Forgiving addresses, same fields. Channel pasted in the stream-link field
  is watched as the channel; a video link pasted in the channel field is
  watched as the video; a channel page as a "video id" no longer becomes a
  garbage id no player could open. The three fields (stream link, channel,
  Facebook link) are unchanged and still edited in Live stream — paste
  whichever form you have.
- Files go to the joined disk. Backup export/import and the live backfill
  used serverUrl(), which on `npm start` names the live site (stamped from
  cms-server.txt) while the socket — and the disk — are local: restored
  photos/videos landed on live's short memory and the local disk stayed
  empty, while the toast reported success. They now use the joined backend
  (local disk when a same-origin server is injected, else the office
  address), so a live backup restored on local shows its photos/videos.
- The push is followed to live. After "new words pushed", the terminal now
  watches the live version.json until it catches the baked update ("live is
  on update N — the last publish is sleep-safe") — or warns loudly if it
  never does, with the by-hand fix. Publish locally, wait for the
  sleep-safe line, and sleep cannot touch last-published.
- Local → live is unchanged: publish locally, the bake + commit + push go
  out by themselves in ~2 minutes, Render rebuilds, the bake carries the
  whole publish (words + stamp + history + uploads).
- Unchanged and still locked: every new update holds on maintenance until
  the office publishes (plain reload, /admin clear); with no new update
  the copy stays on the last published; only an explicit office action
  lifts maintenance; sleep/wake re-serves the last publish whole.
- The pre-ship verifier's section L now locks the fold (no hand button, fold
  on both publish paths, office edits win, uploads come home) — one FAIL
  blocks the ship. It passed for this zip.

LOCAL (your computer)
1. In the OLD folder: open #/admin → Tools → Back up now. Keep the file.
2. Extract THIS zip to a NEW folder (do not extract over the old one).
3. In the new folder: npm install
4. Use `npm run dev` for local work (http://localhost:5173/, admin: /admin).
   Do NOT run `npm start` on the office machine: sharing ships ON in this
   folder, and a local `npm start` would re-point cms-server.txt at this
   machine's tunnel (the live site must keep pointing at Render).
5. BEFORE restoring: the site must show the maintenance notice ("We'll be
   right back", logo + message only) — this update holds until blessed.
   A plain reload must show it; no hard refresh needed. The admin console
   (/admin) must NOT show it — it boots straight into the console.
6. Bring your words home: #/admin → Tools → Restore the backup file → review
   → Publish. The Publish itself folds in anything newer on the live site
   (untouched sections follow live, your edits win, uploads come home), so
   there is no second step anymore. Restored photos/videos land on THIS
   disk now (the 310 fix) — check a photo field after publishing.
   Local lifts to 312 and the notice releases. Reload desktop + phone
   width to verify (plain reloads).
7. From here the sync is automatic both ways: publish on LOCAL and the
   bake + push carry it to live in a few minutes (watch the terminal for
   "auto-deploy: new words pushed", then `git log --oneline -3` shows the
   content commit) — then wait for the follow-up line "live is on update N
   — the last publish is sleep-safe" (the 310 watch: it polls the live
   version.json until the rebuild lands). If instead it warns that live
   has not caught up, open the host dashboard (Render: Deploys tab) and
   get the rebuild through — UNTIL THEN a sleep would bring back the older
   publish, so treat the warning as a job, not a note; publish on LIVE and
   the signed-in office copy saves it
   by itself within about a minute (toast confirms, uploads included) — or
   it folds into the next local Publish, whichever comes first — and the
   deploy carries it back out on the next cycle. WITHOUT the step-7
   push the live bake goes stale and a live wake waits on maintenance
   again — if the terminal reports a bake/push problem it now says why.
8. Check: reload again with no new update — the site stays on the last
   published (no notice, published words intact). Console check:
   window.__maintState() shows publishedNotes 312.

LIVE (Render: twocchurch-site.onrender.com)
1. Put this code where Render builds it (replace src/, scripts/, index.html,
   seed.json, vite.config.ts, package.json — keep data/ as-is), commit/push.
   Render: install npm install, build npm run build, start node scripts/serve.mjs.
2. Confirm https://twocchurch-site.onrender.com/version.json shows {"notes":312}.
3. Push the step-7 content commit if you have not already (the bake must be
   from 312 or newer — a bake stamped 311 or older still waits, by design).
   Render rebuilds on the push by itself.
4. The live site now waits on the maintenance notice until the publish lands
   through the bake — verify with a PLAIN reload on desktop + phone width,
   uploads/photos/videos showing. The live admin console stays clear
   throughout and keeps "Last published". A live /admin publish now also
   lands on the office copy by itself (about a minute, while the office is
   signed in) — but still publish the same words locally afterwards when
   you can: the ephemeral disk forgets, the office folder remembers.
5. Sleep test (optional, proves the fix): in the Render dashboard, restart
   the service (or just wait for it to sleep). The site must stay live with
   "Last published" intact — no notice, no re-publish. If the notice shows,
   the bake is stale: do step 7 first, then test again.
6. Optional but recommended on free Render: a free keep-awake ping
   (e.g. UptimeRobot, every 5 minutes, to
   https://twocchurch-site.onrender.com/version.json) skips the 30–60s cold
   boot after a sleep. Harmless either way now — sleep loses nothing — it
   only makes first loads faster.
